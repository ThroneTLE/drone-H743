# 类别模式：算法验证

适用于目标是**判断某个算法在真实数据上表现如何**的 REQ——估计、滤波、补偿、
控制律、标定解算。不适用于改代码结构（那是常规 REQ）。

## 授权

- 新建 host 侧回放、复算、对比脚本（放 `tools/`，遵守新功能新模块）
- 只读读取 `data/**` 下的全部历史记录与飞行日志
- 用 Python 独立复算一遍固件里的同一段数学，做数值交叉验证
- 建离线 harness，把固件的 C 函数直接编到 host 上跑

## 判据（验收看这几条，不看"测试绿不绿"）

1. **结论必须落在实录数据上。** 自己构造的输入只能用于单元测试，
   **不能**用来下"算法正确/收敛/达标"的结论。这条没有例外。
2. 必须给出**基线版本与待判版本在同一份数据上**的逐项对比，
   而不是各跑各的数据集然后比结果。
3. 必须写清**失败模式和适用边界**：这个算法在什么条件下不成立。
   只报"通过"而不报边界的交付一律打回。
4. 数值容差要说明**来源**（传感器量化、定点精度、采样率），
   不许先看到结果再倒推一个刚好能过的阈值。

## 禁止（未经作者单独批准）

- **改控制律、滤波器系数、PID 参数**——那是冻结副线 S4/S5。
  「验证」不等于「整定」：你可以证明当前参数好或不好，
  但换参数是另一件需要立项的事。
- 改任何安全门限、判据阈值、坐标符号。
- 拿"算法上更优"当理由绕过 PIPELINE 的节点顺序。

## 交付物

除常规交付外，附：所用数据集路径、基线与待判版本的对比表、边界结论、
复算脚本路径。
