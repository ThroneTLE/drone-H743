# 工作模式：默认执行、修 bug 与按需类别

角色和协作由 [项目 SKILL](../SKILL.md) 与 [主控规则](dispatcher-prompt.md) 定义；
验证时机与范围统一见 [验证策略](validation-policy.md)。类别模式只增加本领域必要判据，不恢复逐人全量或共同修改总表的旧流程。

## 默认模式

主控承接作者目标，执行者只做任务卡。作者只讨论时不认领任务；实机工作须明文授权。
普通文档、局部实现/修复已有边界时直接执行，不因缺少某个类别文件停下来要求作者补模板。
任务明确指定类别模式时先读；发现授权或判据确实缺失时由主控澄清必要问题，只有新的专属规则值得长期复用才增加模式。
交付简要注明用过的模式及原因；子 Agent 完成后交待审核，主模型审核改动与证据，决定通过或返修，统一维护 PIPELINE 状态与索引。

## 修 bug 模式

当前任务就是修 bug，或发现阻塞任务/让验收无法通过/会把错误数据当证据的缺陷时进入。
风格、命名、顺手重构和与目标无关的微优化不随修复扩张。

1. 先固定现象：报文、计数、复现步骤、受影响证据；再解释根因以及原测试为何没挡住。
2. 只改根因；回归基准来自真实固件格式、真实 C 实现、已确认实录或回读，不能把自己的假设同时写进实现和测试。
3. 按验证策略覆盖缺陷和原行为。执行者只修自己文件范围内的根因；涉及其他人范围或公共架构，交主控协调，避免多人抢修。
4. 独立 fix 提交与独立证据项由主控集成归档，保留失败信息；不要求子 Agent 编辑 PIPELINE。完成后继续原任务。

安全门/判据/坐标符号、CubeMX 生成代码、历史标定证据、需要实机才能确认的动作，仍按各自授权边界处理；修 bug 不自动扩大权限。
