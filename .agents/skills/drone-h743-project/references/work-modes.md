# 执行者工作模式

模式不是固定枚举，是可以长出来的。本文件定义**机制**：默认怎么做、
撞上缺陷怎么办、以及**任务类别模式**怎么挂载进来。

具体某一类任务（算法验证、协议改动、标定解算……）的规矩，
写在 `references/modes/<类别>.md` 里，由派发者在**首次派发该类任务之前**写好。
派发者侧的写法见 [dispatcher-prompt.md](dispatcher-prompt.md)。

## 三层结构

| 层 | 是什么 | 谁写 |
|---|---|---|
| 默认层 | 常规 REQ 执行，永远生效 | 本文件 |
| 横切层 | 修 bug 模式，任何任务都可能触发 | 本文件 |
| 类别层 | 该类任务专属的授权与判据 | 派发者，见 `modes/` |

接单时：读 REQ → 若 REQ 指定了类别模式，先读那份 `modes/<类别>.md` → 再动手。

**REQ 属于某个类别但 `modes/` 里没有对应文件时，停下来找派发者要，不要自己猜。**
缺一份类别模式说明这类任务还没被想清楚，硬做出来的东西大概率要返工。

---

## 默认层：常规 REQ 执行

任务来源是 `PIPELINE.md` 的执行需求清单。

- 作者**可以一次派发多个 REQ**，连续做完一次性交审，不必做一个停一个。
- 没指定时，取当前主线节点直接需要的、状态为「待做」的〔码〕类 REQ。
- 〔机〕〔人〕类不归你：实机归审核者，物理操作归作者。
- 交付说明里注明本次进过哪些模式、每次为什么进。

## 横切层：修 bug 模式

老规矩「REQ 之外的发现只写进交付说明、不动手」在遇到**挡路的缺陷**时
会让整条线停摆，或者更糟——让错误结论被当成证据存档。所以单独开一个口子。

### 进入条件（满足任一）

- 缺陷**阻塞当前 REQ**，不修做不下去。
- 缺陷让 PIPELINE 里某条验收**永远不可能通过**。
- 缺陷会导致**错误的数据被当成有效证据**保存下来。

> 真实案例（2026-08-30，M5 台架）：上位机解析器只认 `gz_dps`/`gz_mdps`，
> 而固件按 `units=mg_mdps_cdeg` 发的是裸 `gz`。两个名字固件从没发过，
> 于是旋转补偿阶 299 个实采样本无一带偏航角速度，这一阶**从来没有过关的可能**。
> 它不抛异常、不报错，只是安静地让一整阶验收做不完。
> **安静失败比崩溃危险得多**，这类缺陷必须当场修。

### 不进入

风格、命名、"我觉得能更好"、性能微优化、想顺手做的重构——写进交付说明，不动手。

### 流程（顺序不可省）

1. **先固定证据，再动手。** 把缺陷的可观测事实记下来：计数、报文原文、
   复现步骤、受影响的证据文件。修完之后你就再也证明不了它存在过。
2. 定位根因，并回答一句：**"为什么现有测试没挡住它？"**
   答不上来，说明你还没找到真根因。
3. **最小修复面**：只改根因。顺手重构 = 打回。
4. **回归测试的基准必须取自真实来源**——固件源码里的格式串、实录数据、
   硬件回读值。自己编一行样例报文当基准，等于把同一个错误抄进测试里。
5. 单独提交（`fix(...)`），在 PIPELINE 证据表**单独追加一行**，
   写明缺陷、根因、为什么没被挡住。
6. 回到原 REQ 继续。

### 必须升级给作者、不得自行修

即使你确信它是错的：

- 安全门、判据阈值、坐标符号
- CubeMX 生成代码
- `data/calibration/**` 历史证据
- 任何需要动实机才能确认的缺陷（实机归审核者）
