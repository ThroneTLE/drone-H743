# 解耦开发规范（新增模块 / 重构 / 优化前必读）

本文件把解耦从"感觉"变成**可判定的规则**。判据只有一句：

> 当某一部分发生变化时，其他部分**凭什么**可以完全不知道、不受牵连？

它同时是 Agent 作业规范——**Agent 的能力上限受限于代码耦合度**。
巨石文件里 Agent 只能猜，独立模块里 Agent 能被单测判对错。所以下面每条规则
既是架构要求，也是"这个任务能不能交给 Agent 做"的前提。

分层目录、文件规模上限、FLU 契约的**权威定义**在 [`../SKILL.md`](../SKILL.md)
和 [flu-coordinate-contract.md](flu-coordinate-contract.md)，本文不重复，只补"为什么"和"怎么判"。

新增/改动前先继承 [已采纳设计](../../../../doc/current-architecture.md)；本规范不授权后续 Agent 按个人偏好推翻职责与接口。
公共边界变化交主控协调，验证范围统一见 [验证策略](validation-policy.md)，执行者不因本文件另行全量或更新公共索引。

---

## 0. 五个维度总览

| 维度 | 解耦对象 | 自检问题 | 本仓库锚点 |
|---|---|---|---|
| 1 硬件与生命周期 | 算法 ↔ 芯片 / PCB / CubeMX | CubeMX 重生成、传感器换型，算法要改一行吗？ | `Core/` vs `App|Services|Driver|BSP/` |
| 2 时间与节拍 | 高频硬实时 ↔ 低频阻塞 I/O | Flash 擦写卡 30ms，姿态环会停吗？ | `StabilizerTask` / `backgroundTask` |
| 3 数据与控制流 | 模块 ↔ 模块 | 换一个姿态估计器，控制器要改吗？ | `APP_Sensor_SampleMessage` 等消息体 |
| 4 语义与契约 | 各层对同一物理量的约定 | 谁负责把芯片轴向转成机体 FLU？ | `Driver/Inc/drv_frame_contract.h` |
| 5 可测性 | 算法 ↔ 单片机 / RTOS | 不烧录能验证吗？ | `tests/` + `data/` |

维度 5 是前四个维度的**验收测试**：能在 PC 上测，说明硬件、时序、全局状态、
隐式约定都已经被隔离出去了。

## 1. 维度一：硬件与生命周期

"生命周期"有三层，三层各有各的隔离手段。

| 生命周期 | 现象 | 规则 |
|---|---|---|
| 工具链 | CubeMX 每次 Generate 全量刷新 `Core/Src/main.c`、`freertos.c` | `Core/` 归工具管，业务**一行都不写在** `USER CODE` 区；只在极薄入口挂接一次 |
| 硬件迭代 | 算法寿命 5~10 年，元器件 1~2 年（停产 / 改版 / 换总线） | 换芯片只动 `Driver/` + `BSP/`；`App/`、`Services/` 不动 |
| 运行态 | 上电时序、自检延时、握手都可能失败 | 硬件走自己的状态机；上层只消费**数据 + 健康标志**，不直接操控复位时序 |

**D1-1** 业务代码禁止出现在 CubeMX 生成文件里。需要改引脚 / 时钟 / DMA / NVIC /
RTOS 对象时，按 SKILL.md 的流程告知作者去 CubeMX 改，等重新生成后再接线。

**D1-2** `App/` 与 `Services/` 里禁止直接 `#include` HAL 头
（`stm32h7xx_hal*.h`）、禁止直接操作寄存器与片选引脚。硬件访问经 `Driver/` → `BSP/`。

**D1-3** 禁止在初始化路径写 `while (dev_read() != OK);` 这类无界死等。
外设初始化必须有超时和失败出口，失败后进 `FAULT` 态并置健康标志，
**由上层决定降级还是拒飞**，不是把整机卡在初始化里。
> 这条是保护逻辑：一颗传感器松动就让看门狗反复复位，比缺一路数据危险得多。

**D1-4 什么时候必须新建 `Services/` 模块。**`Driver/` 说的是"芯片方言"，
`App/` 需要的是"飞行领域语言"。出现下面任一情况时，翻译层必须独立成 Service，
不能塞进 App 任务：

1. **语义升维**：原始计数 → 带量程换算、去零偏、温补的物理量。
2. **多源聚合与仲裁**：双 IMU 投票、参数落内部 Flash 还是外部 Flash。
3. **执行契约**：芯片轴向 → 机体 FLU 的装配变换（见维度四）。
4. Service **不占独立 RTOS 任务**、同步、纯被动，由调用者在自己的节拍里调。
   需要独立节拍或会阻塞的，那是 App 任务，不是 Service。

现有 Service：`svc_param`、`svc_timestamp`、`svc_flow_nav`。新写的按同样形态。

## 2. 维度二：时间与节拍

> 有调用关系 ≠ 必须在同一个周期里运行。

不同物理量的时间尺度差数万倍：电机换相 µs 级、角速度响应 ~1ms、姿态角 ~4ms、
气压 / GPS 20~100ms，而 Flash 擦写与日志落盘是**偶发 10~50ms 阻塞**。
把它们放同一条循环里，卡一次就丢 30 拍。

更隐蔽的杀手是**抖动**：离散 PID / 卡尔曼的推导前提是采样周期 Δt 恒定。
这一拍 1ms、下一拍 31ms，微分项 `(e[k]-e[k-1])/Δt` 会炸出巨大噪声。

**D2-1** ISR 只做搬数据 / 置标志 / 唤醒任务，重活交给 Task。

**D2-2** 高频控制路径（姿态环及其以下）禁止任何可能阻塞的调用：
Flash / 日志落盘 / 长打印 / 阻塞式总线等待 / 不带超时的锁。
这类工作交给 `backgroundTask`，见 [runtime-services.md](runtime-services.md)。

**D2-3** 控制器与滤波器的 Δt **必须来自真实时间戳差值**（`svc_timestamp`），
不得写死成名义周期。名义周期会把调度抖动伪装成"没有抖动"。

**D2-4 按数据语义选机制，不按"总线"选。**

| 数据语义 | 例子 | 机制 | 读者数 |
|---|---|---|---|
| 数据到了立刻算（唤醒） | IMU DRDY → 内环 | 信号量 / Task Notification，直读缓冲，零拷贝 | 1 |
| 只要最新值，旧的丢了无所谓 | IMU、姿态、RC、电压 | Mailbox（深度 1 + overwrite/peek）或全局结构体 + 临界区拷贝 | N |
| 一条不能丢，按序处理 | 命令、模式切换、日志流 | 深度 N 队列 / SPSC RingBuffer | 1 |
| 纳秒级时序，CPU 别碰 | PWM / DShot | 定时器 + DMA | — |

**状态类数据不要用 FIFO 语义**：消费者慢一拍，队头堆的就是旧帧，
用 10ms 前的姿态算出的控制量会引入相位滞后。飞控只要最新鲜的一帧。

本仓库现状：`SensorSampleQueue`（深度 8）与 `uartTxQueue` 采用
**"满则丢最旧再入队"**的手写覆盖模式（`osMessageQueuePut` 失败 → `Get` 一个 → 重 `Put`）。
新代码遇到同类需求**沿用这个已有模式**，不要再引入第三种写法；
确实需要"深度 1 最新值"时用 `xQueueOverwrite`/`xQueuePeek`，
并且 **peek 超时必须给 0**，节拍来自 `vTaskDelayUntil`
（`portMAX_DELAY` peek 深度 1 的队列 = 忙等死循环）。

**D2-5 不要过度设计。** 几十字节的结构体，Mailbox 或"全局结构体 + 临界区拷贝"
就够了；三缓冲 / 带订阅者列表的微总线是 PX4 uORB 那种规模才值得上的东西，
在本仓库引入需要作者批准。反过来，真上了无锁结构，索引必须 `volatile`
或在写数据与更新索引之间加 `__DMB()`——单核原子读写挡不住编译器重排。

## 3. 维度三：数据与控制流

巨石文件不是因为功能多，是因为一堆全局变量：A 改一点、B 读一点、C 偷偷加个判断。

**D3-1 模块之间只认数据帧，不认对方的内部函数。** 上游发布结构体快照，
下游订阅它。换掉估计器实现，控制器一行不改——做不到就说明还耦合着。

**D3-2 决策与算力分离。**
- 状态机（FSM）：只回答"现在是什么模式"（解锁 / 起飞 / 定高 / 失控保护）。
- 纯算力模块（滤波 / PID / 分配）：输入 `(setpoint, measurement, dt)`，
  输出 `actuator_cmd`。不关心飞机为什么飞，不读全局状态，不调 RTOS，不调 HAL。

**D3-3 新算法模块必须是纯函数形态**：状态显式放在调用者传入的 context 结构体里，
不用文件级可变静态量。这是它能被 PC 单测的前提，也是维度五的入口。

**D3-4** 禁止向 `tools/drone_tcp_panel.py` 与 `App/Src/app_control.c` 追加内容
（SKILL.md 硬约束）。新功能开新模块并接线，参照 `App/Src/app_stabilizer.c` 的拆分先例。

## 4. 维度四：语义与契约

工程后期炸裂的隐蔽元凶：同一个物理量在各层的约定不一致——驱动给的是芯片轴向、
估计器用 NED、控制用 FLU、协议下发又是翻了符号的百分比。

**D4-1** 机体坐标系的唯一权威是 `Driver/Inc/drv_frame_contract.h`。
任何涉及 IMU 轴向、融合 / 导航变换、控制器符号、RC 方向、光流轴、
舵机 / 电机极性的改动，**先读** [flu-coordinate-contract.md](flu-coordinate-contract.md)，
改完跑 `python -m pytest tests\test_flu_frame_contract.py -q`。

**D4-2** 传感器数据出模块前必须已映射到 FLU。
**不允许把符号翻转留给下游滤波算法去猜**。

**D4-3 契约写在头文件里，不写在别人脑子里。** 跨模块传递的物理量，
其**坐标系、单位（SI）、符号约定、时间戳来源、量程**必须在公开头文件的
类型定义处注明。口头约定和只存在于文档里的约定不算契约。

## 5. 维度五：可测性

> 终极检验：核心算法能脱离单片机，在 PC 上跑单测吗？

**D5-1** 新增或修改算法模块时，同一个任务里补 `tests/` 下的宿主侧测试。
做不到说明 D1-2 / D3-3 没做干净——**先解耦，再写测试，不要为了测试去 mock HAL**。

**D5-2** 关于**算法行为**的任何结论，必须落在 `data/` 的实录数据上，
并与基线在**同一份数据**上对比。自己构造的输入只能做单元测试，
不能用来下"算法达标"的结论。

**D5-3** 宿主工具解析固件输出时，测试夹具必须锚定固件**真实发出的格式**
（源码里的格式串或实采报文）。固件从没发过的字段名会**安静失败**，
不报错、不崩溃，只是让一整阶验收永远不可能通过。

## 6. 每张工单的"架构三件套"

派发和自我约束都用这三条，缺一条就说明任务还没想清楚
（派发者侧写法见 [dispatcher-prompt.md](dispatcher-prompt.md)）：

1. **Contract（输入 / 输出边界）**：模块放哪层、公开接口签名、数据结构、
   坐标系 / 单位 / 时间戳来源。
2. **Boundary（隔离区）**：允许依赖什么、**禁止**依赖什么
   （典型禁令：不含 HAL 头、不含 RTOS 调用、不做 I/O、不碰全局状态）。
3. **Test Seam（验收缝）**：在 PC 上用哪个测试、用哪份 `data/` 数据、判据是什么。

**反例与拆解**——"帮我写个磁力计功能，读 QMC5883L 算航向角，在主循环里打印"：
I2C 读寄存器、反正切、打印、延时会全部揉进一个文件，无法单测。正确拆成三张工单：

| 工单 | 层 | 职责 | 禁令 |
|---|---|---|---|
| 1 | `Driver/` | 寄存器配置、读原始三轴 | 禁止数学解算、校准、RTOS 代码 |
| 2 | `Services/` | 硬磁 / 软磁校准，按 FLU 映射，`mag_service_get_field_gauss()` | 禁止占用独立任务；必须带 PC 侧离线单测 |
| 3 | `App/` | 导航任务取校准后磁场，融入观测器 | 禁止直接访问驱动 |

## 7. 提交前自检

- [ ] 改的是不是 CubeMX 归属文件？（是 → 走 CubeMX 流程，不手改）
- [ ] `App/` `Services/` 里有没有混进 HAL 头、寄存器、片选？
- [ ] 高频控制路径上有没有新增可能阻塞 10ms 以上的调用？
- [ ] 新的跨模块数据：语义是"最新值"还是"不能丢"？机制选对了吗？沿用已有模式了吗？
- [ ] Δt 来自真实时间戳而不是名义周期？
- [ ] 新结构体 / 接口的坐标系、单位、符号、时间戳来源写进头文件了吗？
- [ ] 涉及轴向 / 极性 → 跑了 `tests\test_flu_frame_contract.py` 吗？
- [ ] 新算法能在 PC 上跑吗？测试加了吗？算法结论有 `data/` 实录支撑吗？
- [ ] 有没有往 `app_control.c` / `drone_tcp_panel.py` 追加内容？
- [ ] 文件是否逼近规模上限（C ~1500 行 / Python ~2000 行）？该拆了吗？
- [ ] 交付已列明源码/测试/文档变化，主控合并收尾后统一运行索引生成与检查了吗？

## 8. 什么时候可以不按这份规范

只有一种情况：**在既有巨石文件里做最小面积的缺陷修复**。
此时按修 bug 模式（[work-modes.md](work-modes.md)）只改根因，
把"这里应该拆开"写进交付说明，不要顺手重构——顺手重构会被打回。

除此之外的偏离（引入新 IPC 机制、跨层依赖、削弱契约、绕过测试缝），
都必须先跟作者说明理由并取得同意，然后记进 `PIPELINE.md`。
