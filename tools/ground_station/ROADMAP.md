## 一、整体框架

整套体系分四层，自下而上依赖。**下层没打通就做上层，等于在流沙上盖楼** —— 早期的
`.ssproj` 就是跳过第 1、2 层直接做第 4 层的产物，结果做出来的是个连不上真机的演示壳。

```text
┌─────────────────────────────────────────────────────────────┐
│ L4  应用功能                                                  │
│     自检向导 · PID 调参台 · 日志回放 · 3D 姿态                  │
├─────────────────────────────────────────────────────────────┤
│ L3  上位机载体                                                │
│     Serial-Studio(GPL3 stock) + 控制脚本(JS) + 扩展包(QML)     │
│     ※ 结论：不 fork。见 README 第 5 节                         │
├─────────────────────────────────────────────────────────────┤
│ L2  安全契约                                                  │
│     Action 生命周期 · 互锁 · 超时 · 心跳 · 急停                 │
│     ※ 上位机不持有危险动作的时间轴                              │
├─────────────────────────────────────────────────────────────┤
│ L1  协议契约                                                  │
│     遥测通道 schema(TELEM?) · 命令契约 · 分帧                   │
│     ※ 单一事实源在固件，上位机自动跟随                          │
└─────────────────────────────────────────────────────────────┘
```

### 贯穿全层的两条原则

**原则 A —— 单一事实源在固件端。**
凡是"上位机需要知道飞控内部结构"的信息（通道映射、命令表、参数量程），都由固件通过
查询接口下发，上位机自动跟随。任何写死在上位机里的映射都会漂移，而且漂移**不报错**，
只是数值看起来"有点怪"。

**原则 B —— 危险动作的时间轴闭环在固件端。**
判据：上位机进程被 `kill -9`，物理世界会不会停在危险态？会 → 必须是 Action。

### 2026-08-29 · 子模块 → subtree（L3）· `5611989` + subtree 提交

子模块机制的根本问题：主仓库只存一个 commit 指针，代码在独立仓库。后果是克隆主仓库
拿不到地面站，且子模块提交忘了推就会让别人构建不出来 —— 本仓库已经踩过。在多 agent
并行改动的场景下，这种靠纪律维持同步的机制风险偏高。

改为 **git subtree（`--squash`）** 并入：普通 `git clone` 即得完整可构建的地面站。

- 跟踪文件 5234 个；`--squash` 避免了把上游 3654 次提交、477 MB 对象库拖进主仓库
- 转换前已将子模块对象导入主仓库，`4bbf511` 的内容完整保留
- `build/`（731 MB 构建产物）在转换中保留并恢复；仅丢失 140 个 `__pycache__/*.pyc`
- 追上游用 `git subtree pull --squash`，见 [README 第 8 节](README.md)

## 四、关键决策记录

记录**决策、理由、以及是什么证据改变了它** —— 避免后来者重走一遍。

### D1 · 上位机载体：全量 fork → 不 fork（2026-08-29 推翻）

- **原决策**：fork Serial-Studio，把 Action Manager、参数缓存、自检向导写进 C++/QML
- **推翻证据**：widget extension 机制在 GPL3 构建里可用（官方文档明确非 Pro，内置
  compass/datagrid 即用此机制），且 `ApiTerminalBridge` 与扩展必须导入的
  `ExtensionDataModel` 注册在同一 QML 模块、同一次调用、`BUILD_COMMERCIAL` 门控之上
- **影响**：原本预计数周的 C++ 工作量收敛为零；无 rebase 成本
- **保留**：fork 本身留着没坏处（已编译好，且承载 Qt 6.7 移植补丁），只是**工作不往
  C++ 里放**

### D2 · 交互控件：Canvas/Painter → widget extension（2026-08-29）

- Painter 有全套鼠标事件和 `deviceWrite`，看起来最适合做 PID 滑条 —— 这正是它的陷阱
- SPDX 为 `LicenseRef-SerialStudio-Commercial`（**非双授权**），整个文件被
  `#ifdef BUILD_COMMERCIAL` 包住；改 ifdef 属于授权问题不是技术问题

### D3 · 遥测通道：写死映射 → `TELEM?` 自动建表（2026-08-29）

- 通道内容本身是**暂定的**，会按实际需求调整 —— 所以关键不是通道内容，而是**机制**
- 机制保证：固件改通道，上位机自动跟随，且不会静默错位

### D4 · Action 验证路径：HIL → host 纯状态机（2026-08-29）

- 曾以为 `feat/hil-simulink-validation` 分支能验证 Action 安全逻辑
- 实查：它是 host 编译的 SIL（不需真机，✅），但只复现 `DRV_COAX_CTRL_Run()`，
  **不含 RTOS 侧、执行器时序、命令层** —— 恰好覆盖不到 Action
- 但它证明了"把固件 C 代码拉到 host 编译并驱动"在本仓库是成熟做法
- **结论**：Action 自己设计成可 host 化的纯状态机。不合并那个分支（提交含 3660 文件 /
  71 万行，绝大部分是采集数据）

### D6 · Serial-Studio 并入方式：submodule → subtree（2026-08-29）

- **原状**：子模块。主仓库只存 commit 指针，代码在 `ThroneTLE/Serial-Studio`
- **问题**：克隆主仓库拿不到地面站；子模块提交忘了推，别人就构建不出来。本仓库已经
  踩过 —— 子模块带着 21 处未提交改动（含必要的 Qt 6.7 构建补丁）裸奔很久没人发现。
  多 agent 并行时，靠纪律维持同步的机制不可靠
- **候选**：① 保持 submodule + 推送纪律 ② subtree ③ vendor 成普通目录
- **取舍**：选 ② —— 单次 `git clone` 即得完整可构建的地面站，同时保留
  `git subtree pull` 追上游的能力（③ 会失去）
- **代价与缓解**：主仓库内会实际存放一份 GPL3 代码。已确认主仓库将来**有可能闭源或
  商业化**，故要求它全部限制在 `tools/ground_station/Serial-Studio/` 单一目录内，
  与固件不链接、非衍生作品，将来整目录删除即可切干净。该边界写在
  [README 5.6](README.md)
- **注意**：并入用了 `--squash`，后续 `git subtree pull` **必须也带 `--squash`**，
  否则历史会打架

### D5 · 混流分帧：暂缓（2026-08-29）

- 曾判断它卡住 `TELEM?`。实查 `vofaStreamActive` 默认为 `0`，连接时取 schema 时序
  天然干净 → **不卡 L1、不卡 L3 只读打通**
- 但流开着时命令回包仍会混在浮点里 → **卡 L2 接线**（Action 状态轮询必然在流开着时发命令）
- 推荐方案：给遥测帧加与文本不可能冲突的魔数头（改动集中）
